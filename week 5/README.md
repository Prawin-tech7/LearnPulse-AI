\# LearnPulse AI — Week 5: Deployment and Monitoring



\## Overview



LearnPulse AI is a student outcome prediction project that demonstrates how a trained machine learning model can be deployed as a REST API using FastAPI and Docker.



The API loads a trained Random Forest classifier and accepts student feature data to generate a predicted class and class probabilities. It also provides health-check and monitoring endpoints.



\## Technologies



\- Python 3.11

\- FastAPI

\- Uvicorn

\- Pandas

\- Joblib

\- Scikit-learn

\- Docker



\## Project Files



\- `app.py` — API endpoints, prediction logic, logging, and metrics.

\- `Dockerfile` — Container configuration.

\- `requirements.txt` — Python dependencies.

\- `save\_model.py` — Trains and saves the model using the processed Week 2 dataset.

\- `models/learnpulse\_model.joblib` — Trained model artifact required by the current API.

\- `logs/` — Runtime logs generated by the API; these are excluded from version control.



\## API Endpoints



| Method | Endpoint | Purpose |

|---|---|---|

| GET | `/` | Returns service information |

| GET | `/health` | Checks whether the model loaded successfully |

| POST | `/predict` | Predicts a student outcome from supplied features |

| GET | `/metrics` | Reports request counts, prediction errors, and latency |



Interactive API documentation is available at `/docs` while the service is running.



\## Run with Docker



Run the following commands from the repository root:



```bash

docker build -t learnpulse-api:1.0 "./week 5"

docker run --rm -p 8000:8000 learnpulse-api:1.0

```



The trained model must exist at `week 5/models/learnpulse\_model.joblib` before building the image.



\## Recreate the Model



The model-generation script uses `week 2/processed\_student\_dataset.csv`. Ensure the processed dataset and the required Python dependencies are available before running:



```bash

python "week 5/save\_model.py"

```



The script trains and evaluates a Random Forest model and saves the model artifact to the Week 5 `models` directory.



\## Testing and Monitoring



Open `http://127.0.0.1:8000/docs` to test the endpoints. Call `/health` to check model availability, `/predict` to test predictions, and `/metrics` to inspect request statistics and prediction latency.



The API writes operational information and errors to `logs/api.log`. The metrics are stored in memory and reset when the application restarts, so this implementation is a proof of concept rather than a production monitoring platform.



\## Limitations and Maintenance



Predictions are model estimates, not guarantees. The encoded target classes must be interpreted using the mapping established during data preprocessing. Monitoring should include request failures, response latency, input validation, and changes in prediction distributions. Periodic evaluation against newly labelled data is needed to investigate model performance drift.



For production deployment, use persistent monitoring, secure transport, authentication, controlled access to student data, model versioning, and an approved process for retraining and validating models.
